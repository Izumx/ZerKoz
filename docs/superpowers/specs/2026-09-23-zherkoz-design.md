# ЖерКөз — цифровой мониторинг земель и сервис для граждан

Дата: 2026-09-23 · Хакатон ZhambylHub · Кейс «Цифровой мониторинг земель и сервис для граждан»

## 1. Цель

MVP двустороннего сервиса:

1. **Веб-панель инспектора** — карта участков с цветовой индикацией, карточка участка с фотофиксацией, дедлайнами и жизненным циклом нарушения.
2. **Telegram-бот для граждан** — статус заявления по трек-номеру, база знаний, «Народный контроль» (геолокация → фото → описание).

Главный критерий жюри (35%) — замкнутый цикл: житель отправил сигнал в бот → точка появилась на карте инспектора без перезагрузки → инспектор сменил статус → житель получил уведомление в боте.

Организаторы данных не предоставляют — все данные симулируются (seed-генератор + демо-симулятор сигналов).

## 2. Решения

| Вопрос | Решение |
|---|---|
| Стек бэкенда | Python 3.11+, FastAPI, aiogram 3, SQLModel + PostgreSQL 16 (драйвер psycopg 3), shapely |
| База данных | PostgreSQL. Геометрия участков — GeoJSON в колонке JSONB, point-in-polygon — shapely в `services/geo.py`. PostGIS не используется (нет в локальной установке и не на всех хостингах); переход на PostGIS (`geometry` + `ST_Contains` + GiST-индекс) затрагивает только `geo.py` и модель — пункт roadmap. Схема создаётся `SQLModel.metadata.create_all` (Alembic — вне MVP) |
| Стек фронта | React + Vite + TypeScript, react-leaflet, i18next |
| Архитектура | Монолит: один процесс (FastAPI + polling бота в общем asyncio-loop). Бот обращается к слою `services`, не к БД напрямую — позже выносится в отдельный сервис без переписывания |
| Реалтайм | Server-Sent Events (`/api/events/stream`) |
| Хостинг | Пока локально. Код готов к Docker-деплою (Dockerfile добавляется позже) |
| Языки | RU + KZ везде (бот и панель), переключатель языка |
| Данные | Генерируемый seed вокруг г. Тараз + импорт GeoJSON как задел на интеграцию |

## 4. Модель данных

**Parcel (участок)**
- `id`, `cadastral_no` (формат `06-097-123-456`, уникальный), `purpose` (код назначения: ИЖС, сельхоз, коммерция, промышленность, ЛПХ), `area_ha`, `address`, `owner` (фиктивный арендатор/собственник), `geometry` (GeoJSON Polygon, JSONB)
- `lifecycle`: `none | detected | in_progress | resolved | returned`
- `violation_type`: `null | unused | seizure | dump`
- `deadline` (date, nullable), `inspection` флаг первичной проверки (`under_check: bool`)
- `ndvi_series` (JSONB — 12 месячных значений, симуляция), `updated_at`

**Цвет участка вычисляется (не хранится):**
- 🔴 красный — `lifecycle ∈ {detected, in_progress}`
- 🟡 жёлтый — иначе, если `under_check` или внутри участка есть сигнал со статусом `new | checking`
- 🟢 зелёный — всё остальное (включая `resolved`, `returned`)

**Переходы жизненного цикла (остальные запрещены → 409):**
`none → detected` (обязателен `violation_type`), `detected → in_progress` (обязателен `deadline`), `in_progress → resolved | returned`, `detected → resolved | returned`, `resolved | returned → detected` (повторное нарушение).
Просрочка = `lifecycle ∈ {detected, in_progress}` и `deadline < today`.

**Signal (сигнал жителя)**
- `id`, `code` (`SIG-0001`), `lat`, `lon`, `description`, `source` (`telegram | demo | seed`), `tg_chat_id` (nullable), `lang` (`ru | kz`)
- `status`: `new → checking → confirmed | rejected`, `confirmed → resolved`
- `parcel_id` (nullable, определяется point-in-polygon при создании)
- `created_at`, `updated_at`

При `confirmed` связанный участок переходит в `detected` (если он в `none | resolved | returned`); тип нарушения инспектор указывает в том же действии (по умолчанию `dump`). Когда участок переходит в `resolved | returned`, все его сигналы в статусе `confirmed` автоматически становятся `resolved`. Любая смена статуса сигнала → уведомление жителю, если `tg_chat_id` задан.

**BotUser** — `chat_id` (PK), `lang` (`ru | kz`), `created_at`.

**Photo** — `id`, `path`, `parcel_id` (nullable), `signal_id` (nullable), `source` (`inspector | citizen`), `created_at`. Фото сигнала также видны в карточке его участка.

**Application (заявление)** — `track_no` (`KZ-2026-042`), `applicant` (фиктивное ФИО, маскированное), `type` (одна из 3 процедур базы знаний), `stage` (`review | inspection | approved | rejected`), `note_ru`, `note_kz` (пояснение), `updated_at`.

**Event (журнал)** — `id`, `entity` (`parcel | signal`), `entity_id`, `action`, `payload` (JSON), `created_at`. Используется для истории в карточке и публикуется в SSE.

## 5. API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/parcels` | FeatureCollection всех участков с `color`, `overdue`, счётчиком сигналов |
| GET | `/api/parcels/{id}` | карточка: атрибуты, фото, сигналы, история, NDVI |
| PATCH | `/api/parcels/{id}` | `lifecycle`, `violation_type`, `deadline`, `under_check` (валидация переходов) |
| POST | `/api/parcels/{id}/photos` | загрузка фото (multipart) |
| GET | `/api/signals` | список сигналов (фильтр по статусу) |
| GET | `/api/signals/{id}` | детали сигнала |
| PATCH | `/api/signals/{id}` | смена статуса (+ уведомление жителю) |
| GET | `/api/applications/{track_no}` | статус заявления (используется и ботом через сервис) |
| GET | `/api/stats` | счётчики по цветам, просрочки, сигналы за сутки |
| GET | `/api/export/parcels.csv` | экспорт реестра |
| GET | `/api/events/stream` | SSE: `signal.created`, `signal.updated`, `parcel.updated` |
| POST | `/api/demo/signal` | создать симулированный сигнал (для демо-страховки) |

Фото отдаются как статика `/uploads/...`. Собранный фронт — `/`.

## 6. Telegram-бот

- `/start` → выбор языка (🇷🇺 Русский / 🇰🇿 Қазақша) → главное меню (reply-клавиатура):
  📄 Статус заявления · 📚 База знаний · 🚨 Народный контроль · 🌐 Язык
- **Статус заявления**: бот просит номер; принимает `KZ-2026-xxx` (заявление) и `SIG-xxxx` (свой сигнал), регистр/пробелы нормализуются. Ответ: этап с эмодзи, пояснение, дата обновления. Неверный формат / не найдено — понятная подсказка с примером.
- **База знаний**: inline-кнопки трёх процедур — изменение целевого назначения, продление договора аренды, участок под ИЖС. Каждая: шаги, список документов, сроки, стоимость/бесплатно, inline-кнопка-ссылка на eGov.kz.
- **Народный контроль (FSM)**:
  1. кнопка «📍 Отправить геолокацию» (`request_location`) — или вложение-локация;
  2. фото (1–3, кнопка «Готово» после первого);
  3. краткое описание (текст, до 500 символов);
  4. сводка + «✅ Отправить / ❌ Отмена».
  Некорректный ввод на шаге → повтор подсказки. После отправки: номер `SIG-xxxx`, привязанный кадастровый номер (если найден), обещание уведомить.
- **Уведомления**: при смене статуса сигнала инспектором бот пишет жителю на его языке.
- Язык пользователя хранится в таблице `BotUser` (`chat_id`, `lang`).
- Без `BOT_TOKEN` бот не стартует, панель работает, в лог — предупреждение.

## 7. Панель инспектора

- **Шапка**: название, переключатель RU/KZ, кнопка «Симулировать сигнал» (демо), индикатор SSE-подключения.
- **Левая колонка**: карточки-счётчики (🟢/🟡/🔴, просрочено, новых сигналов), вкладки «Участки / Сигналы», поиск по кадастровому номеру, фильтры по цвету и типу нарушения, экспорт CSV. Клик по строке → карта летит к объекту и открывает карточку.
- **Карта** (центр): полигоны с заливкой по цвету, маркеры сигналов (новые — пульсирующие), легенда, переключатель подложки «Схема (OSM) / Спутник (Esri World Imagery)».
- **Правая выезжающая панель**:
  - *Участок*: атрибуты, бейдж цвета, stepper жизненного цикла с кнопкой следующего допустимого шага, выбор типа нарушения, дата дедлайна (просрочка подсвечена), галерея фото с загрузкой, график NDVI (sparkline, подпись «симуляция, готово к подключению Sentinel Hub»), связанные сигналы, история событий.
  - *Сигнал*: фото, описание, координаты, привязанный участок (ссылка), кнопки «Взять в проверку / Подтвердить нарушение / Отклонить / Устранено».
- **Реалтайм**: при `signal.created` — тост «Новый сигнал SIG-xxxx», маркер появляется, участок желтеет; данные перезапрашиваются. При потере SSE — автопереподключение.

## 8. Данные (симуляция)

`python -m app.seed.generate` (идемпотентно, `--reset`):
- ~30 участков-полигонов (4–6 вершин, 0.05–15 га) в пригородах Тараза (≈42.85–42.95N, 71.30–71.45E), районы с кодом `06-097-…`.
- Распределение: ~18 зелёных, ~5 жёлтых (проверка/сигнал), ~7 красных (разные типы нарушений, часть с просроченным дедлайном).
- 10 заявлений `KZ-2026-001…042` на всех четырёх этапах, включая `KZ-2026-042`.
- 5–6 сигналов-seed с фото-заглушками (генерируются Pillow: цветной фон + подпись).
- NDVI-серии: высокие для используемых, низкие/падающие для неиспользуемых.

`python -m app.seed.simulate` / `POST /api/demo/signal` — случайная точка внутри случайного участка + фото-заглушка + описание из пула.

`python -m app.seed.import_geojson file.geojson` — импорт FeatureCollection: Polygon берётся как есть, Point → квадрат по площади (или 1 га), поля `cadastral_no`, `purpose`, `area_ha` маппятся по именам.

## 9. Обработка ошибок

- Валидация переходов в сервисе → HTTP 409 с понятным сообщением; фронт показывает тост.
- Загрузка: только image/*, до 10 МБ → 400.
- Не найдено → 404. Бот ловит исключения в хендлерах и отвечает «Что-то пошло не так, попробуйте ещё раз» + лог.
- Ошибка отправки уведомления жителю (бот заблокирован) не ломает смену статуса — пишется в лог.

## 10. Тестирование

pytest на реальном PostgreSQL: отдельная БД `<имя>_test` (создаётся фикстурой, таблицы пересоздаются на каждый тест-сеанс, данные чистятся между тестами). URL берётся из `TEST_DATABASE_URL` или выводится из `DATABASE_URL`.
- `geo`: точка внутри/вне полигона, выбор участка.
- `parcels`: допустимые и запрещённые переходы, вычисление цвета, просрочка.
- `signals`: создание с привязкой, смена статуса вызывает notify (фейковый notifier), confirmed → участок `detected`.
- `applications`: нормализация трек-номера, не найдено.
- API: основные эндпоинты через TestClient на временной БД.
Бот — ручная проверка по сценарию демо.
